# ADR-080 · Wazenda webhook: 202 ack and background processing, idempotency by id hash (2026-10-28, Claude Code)

**Context.** T-10, specs/01 (Wazenda retries without a fast response; raw-body HMAC-SHA256 signature).

**Decision.** `POST /webhook/wazenda` reads raw bytes, verifies `X-Wazenda-Signature` with `hmac.compare_digest` (missing/malformed/bad signature/invalid JSON → 401); an event other than `message.received` or with no body/media → 200 `ignored`; `timestamp` older than 300s → 200 `ignored` + `webhook_stale` log; already-seen id → 200 `duplicate`; otherwise `asyncio.create_task` (reference kept in `app.state.webhook_tasks`) and 202. Idempotency in table `webhook_events` (migration 0008) via `Keyring.hash("wazenda:<message_id>")` through definer function `vigia_webhook_first` (the id never in clear, a global table with no business RLS). Ports live in `app.state.wazenda` (`WebhookPorts`), tests inject fakes, production builds them lazily on the first signed request. `WAZENDA_API_KEY`, `WAZENDA_LINE_ID`, and `WAZENDA_WEBHOOK_SECRET` go together or none (`Settings` validator): the API refuses to half-start instead of 500-ing every signed webhook. On shutdown, `lifespan` awaits already-accepted tasks and closes the HTTP client. Business rejections (not enrolled, caps) are 200, never 4xx. Logs carry no body, phone masked. The adapter only downloads media from `https` with the exact host of `WAZENDA_BASE_URL`, streamed with a 10 MB cap; type is decided by magic bytes, not `media_type`; sending retries 3 times on 429 (1/2/4s + jitter) with an in-memory 55 req/min per-line cap.

**Why.** Fast ack per Wazenda's retry policy; idempotency without storing a raw message id; no business logic can fail with a 4xx that triggers retries.

**What would invalidate it.** Traffic that exhausts Postgres connections (then pooling + short transactions, T-16) or message loss on restarts (then a Redis queue).
