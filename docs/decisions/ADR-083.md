# ADR-083 · Webhook: the same media is read once per business; 8 messages in flight per process (2026-10-28, Claude Code)

**Context.** Reviewer T-10 (MAJOR, incident `adv-media-repetida`): `whatsapp.process` downloaded and paid for Voice/Spark/SAM before `ingest.handle`, and dedupe (`save_case`) is keyed by `message_id`, which changes on every forward: the same voice note forwarded 20 times paid for 20 reads. Nothing capped how many messages process concurrently either (each with its own open connection and transaction, D-080).

**Decision.** After downloading and before `asyncio.to_thread(reader)`, `_first_media` claims `vault.hash("media:<business_id>:<sha256 of the bytes>")` in the existing `webhook_events` table (definer function `vigia_webhook_first`, no new migration); if already claimed, it answers `case.duplicate` without calling any reader. The hash includes the business id, so the same file in another business is read separately. The claim lives inside the message's transaction: a concurrent copy waits on the unique index and comes out duplicate; a rolled-back message takes its claim with it. For ogg, the already-converted WAV is hashed (same audio, same hash). Concurrency: `asyncio.Semaphore(WEBHOOK_CONCURRENCY = 8)` around each `process`. Why 8: each in-flight message holds an open Postgres connection while models run (D-080); 8 is a prudent unmeasured figure, plenty for a 2-10 person business. The claim and the read sit inside a nested savepoint: if the read rejects (`MODEL_UNAVAILABLE`, `TOO_LARGE`, `INVALID_ATTACHMENT`…), the savepoint rolls back and resending the same file gets the real reason or a retry, not `case.duplicate`.

**Ceiling.** While one copy is being read, a concurrent one waits on the unique index; if the first fails, the second goes through and pays for its own read; the download itself still repeats; no per-case USD cap yet (D-081); the semaphore is per process; `webhook_events` grows without retention (T-19).

**What would invalidate it.** A file that always fails expensively, resent in a loop (pays every attempt until a per-case USD cap exists), or multiple API replicas (needs a shared queue).
