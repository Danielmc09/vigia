# ADR-110 · The "Try it" form is improved with a single same-origin `panel.js`, whole-section replacement (2026-10-31, Angel + Claude Code)

**Context.** Angel asked for two things: (1) remove the `#resultado` anchor from the form's action (the jump annoys more than it helps) and (2) progressive enhancement with JS, capped at 1 hour: if it's not green by then, revert and keep only (1). The no-JS form already works (POSTs to `/panel`, repaints the whole page); the enhancement had to avoid the reload without duplicating that render logic.

**Options.** (a) inline script in the panel's HTML. (b) a dedicated script in a separate same-origin file, loaded via `<script src>`. (c) a fetch/DOM framework or library.

**Decision.** (b). New `src/vigia/channel/panel.js`, no dependencies; read once at import time (`PANEL_JS`, same pattern as `tlds-iana.txt`) and served at `GET /panel.js` behind the same token as the rest of the panel (the `vigia_panel` cookie travels alone on a same-origin GET, so nothing breaks; keeps the panel "as closed as today"). CSP goes from `default-src 'none'; style-src 'unsafe-inline'` to adding `script-src 'self'; connect-src 'self'` (fetch falls under `connect-src`, which without this inherits `'none'` from `default-src`). The script intercepts submit, disables the buttons, shows "Analyzing…" + a CSS spinner (`.busy::after`, respects `prefers-reduced-motion`), does a `fetch` to the same `/panel`, and replaces the whole `section.try` with the HTML the server already re-rendered (parsed with `DOMParser`). On failure: restores the original buttons and text, shows an error message.

**Why.** (a) and (c) were dropped by explicit instruction: nothing inline, nothing third-party, a single own file. Replacing the whole section instead of only `#resultado` avoids reimplementing in JS what the server already does well (text left in the box, notices, result) — less code, one single source of truth for rendering.

**Text (reviewer, Oct 31).** `panel.js` carries no user text of its own (rule 16): "Analyzing…" and the error come from `i18n` (`panel.try.busy`, `panel.try.error`) as `data-busy`/`data-error` on `section.try`, which the server re-renders, so they survive the replacement.

**Not done.** Nothing is stored client-side; the textarea follows whatever value the server sends in the replaced HTML. Without JS, the form is identical to before (true progressive enhancement).

**What would invalidate it.** If the server changes the fragment it returns and stops including the whole `section.try`, `replaceWith` has nothing to replace and the catch fires the error even though the request was a 200 — check the selector then, not just the fetch.
