# ADR-103 · An attachment is matched to the closest candidate, not the only one (2026-10-31, Claude Code)

**Context.** Real-test incident: a voice note at 14:08:35 UTC and an image at 14:10:04 UTC (89s apart). D-096 required a unique candidate within ±120s, so the image got `MEDIA_MATCH_FAILED`: any second attachment within two minutes killed both. Also, `GET /messages` already carries a signed `media_url` on inbound items with an attachment (verified Oct 31 by Angel, host `www.wazenda.com`), but still no `wamid`.

**Options.** (a) keep requiring a unique candidate — fails whenever someone forwards several scams in a row. (b) closest to the webhook timestamp, with `MATCH_WINDOW` as an outer bound, rejecting only if the two best candidates are closer than `AMBIGUOUS_GAP` to each other. (c) match by arrival order — fragile under retries and out-of-order delivery.

**Decision.** (b) with `AMBIGUOUS_GAP = 5s`. The observed webhook/listing clock offset is ~1s (D-096); a wrong choice requires the distance gap to be smaller than twice that offset (~2s). 5s gives a ×2.5 margin and excludes WhatsApp's multi-forward burst (attachments 1-2s apart), exactly the case where picking one would be guessing. A human forwarding one at a time takes much longer than 5s between messages. If the item carries `media_url` and passes `_trusted`, download it directly (avoids `/messages/{uuid}/media` and its 502 on old media); otherwise use the uuid as before. `_trusted` accepts the base host and its `www.` twin (same provider, the listing arrives over TLS with our key): without this, a real `media_url` would never pass with `WAZENDA_BASE_URL=https://wazenda.com/...`.

**What would invalidate it.** A multi-second webhook/listing offset in production (raise the threshold), or the webhook starting to carry the uuid/`media_url` directly (matching becomes unnecessary).
