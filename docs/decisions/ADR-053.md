# ADR-053 · No cross-business contact oracle: `team` replies the same whether the contact belongs to another business (2026-10-27, Claude Code; revised 3 times after judge T-08)

**Context.** Incident `adv-enumeracion-contacto`: `team +<phone> A <email>` replied `contact.taken` if the contact existed in ANY business, and anyone can become an owner with `hi X CO` → enumeration of other businesses' phones and emails (specs/16).
**Options.** Keep the literal spec wording (leaks); reply neutrally.
**Decision.** Deviation from specs/12 B6. Same business → `contact.taken` (no leak). Different business → the same reply as a successful enrollment (new key `team.request_received`, without actually adding anyone); an email belonging to another business → `email.code_sent` without sending anything, still going through the per-address cap.
**Why.** B6's intent (don't allow a number in two businesses) is preserved; it just stops being observable from outside.
**Revision 1** (incident `adv-enumeracion-reintento`): `contact.taken` for the same business was itself a 2-step oracle (send `team +X` twice: free number → 2nd reply says `contact.taken`; foreign number → both replies say `team.request_received`). Fixed: an already-enrolled phone, anywhere, now always replies `team.request_received` idempotently.
**Revision 2** (incident `adv-enumeracion-tope-correo`): the per-address cap wasn't incrementing for an email already verified in another business (no code row inserted), so a free address would eventually hit `email.code_rate_limited` while a foreign one never would. **Decision:** `store.issue_decoy_code` inserts a decoy row (random 32-byte hash that no 6-digit code can match) that counts toward both caps but is never actually sent or redeemable.
**Revision 3** (incident `adv-enumeracion-codigo-senuelo`): the decoy was born already expired, creating yet another oracle (`email.code_none` vs `email.code_invalid`). Fixed: the decoy now stays live for the normal TTL with an unguessable random hash, so it ages and locks exactly like a real code.
**What would invalidate it.** Support needing to tell an owner why an employee wasn't enrolled → notify via the employee's own channel, not the one enrolling.
