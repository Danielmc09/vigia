# ADR-064 · What the supplier address book exposes to Meta: name, email domain, and last 4 account digits (2026-10-27, Claude Code)

**Context.** `check_address_book` (analyst tool, specs/03) reads the business's decrypted address book and its output travels to the Meta API as a `tool` message. T-09's first version sent the full name, full email, and last 4 account digits. specs/16 requires PII never in clear outside where strictly needed; T-09's reviewer asked to justify or reduce it. What the model needs it for: confirming the sender claims to be a known supplier and comparing the message's email domain and account against known ones (BEC: "we changed accounts"). The exact email/account comparison is already done by rules (`signals/address_book.py`, no model involved).

**Options.** (a) everything in clear (what existed); (b) only `known: true` (the model can't distinguish two partial matches or spot a lookalike domain); (c) name, email domain, and account tail.

**Decision.** (c), in `services/analyst_tools.py:_known`. The mailbox (local part, usually a person's name) and the full account never leave. The name stays: it is the supplier company's name the message itself already mentions, and without it the model can't pick among several matches. Thresholds: `ACCOUNT_END = 4` (what banks and invoices in Colombia and the US show to identify an account without exposing it, and the minimum that tells the old account apart from the message's "new" one; searching by account requires at least 4 digits so a short number like "3 boxes" doesn't pull half the address book). `MIN_PARTIAL = 4`: a shorter query only matches a whole name, so "ace" or "sa" never return half the book; 4 letters already separates short trade names ("acer" finds "Aceros del Norte"). `MAX_MATCHES = 5`: a 2-10 person business has a few dozen suppliers at most; 5 are enough to disambiguate and cap the leak if a broad query matches many.

**Why.** Minimum disclosure that still lets the model do its job; the exact comparison stays in deterministic rules.

**What would invalidate it.** A BEC in the set only detectable by seeing the exact mailbox (e.g. a supplier impersonated via another Gmail account) that rules miss; then a keyed hash of the mailbox is sent for comparison, never the mailbox itself.

**Extension 2026-10-27** (judge T-09) — the case brief (`analyst/loop.py:_brief`) used to send the whole `case.email` (sender, display name, `Reply-To`, `Return-Path`, `Authentication-Results`). The prompt names none of these by name and the exact sender/name comparison against the address book is already done by rules.

**Decision.** The brief sends `email = {sender_domain, reply_to_domain, with_headers}` (via `domain/text.py:mail_domain`, also used by `_known`). Excluded: mailboxes, display name, `Return-Path`, and `Authentication-Results` (which often carries `smtp.mailfrom=<mailbox>`). Domains stay because they are the BEC evidence the model can check with `check_country`/`analyze_url` (lookalike domain, `Reply-To` on another domain) and do not identify a person except on free email (gmail.com, which identifies nobody). The message body still travels whole: it is what gets classified. Accepted risk: the `web_search` query is written by the model and may carry fragments of the text (a name, a phone) into Meta's search; bounded by `triage == "investigate"`, `MAX_SEARCHES = 2`, and the fact that the text already reached Meta in the brief. The query itself is not filtered.

**What would invalidate it.** A BEC only solvable by seeing `Authentication-Results` (then only the spf/dkim/dmarc verdict is sent, no addresses).
