# ADR-096 · WhatsApp attachments matched by strict listing, not "latest" (2026-10-31, Claude Code)

**Context.** T-10e: an attachment's webhook carries `[audio]`/`[image]`/… and the `wamid`, but no `media_url` and not the uuid `GET /messages/{uuid}/media` needs. It was being judged as plain text ("unclear").

**Options.** (a) take the most recent inbound message with `media_type` (what the spec said) — with two attachments in a row, or an old one, it analyzes the wrong one. (b) strict match: list `contact=<digits>&limit=5`, accept only inbound entries with `media_type`, same `contact_number`, a valid uuid `id`, and `created_at` within ±120s of the webhook; exactly one or none. (c) wait for the provider to send the uuid.

**Decision.** (b), plus (c) requested from Angel. `Wazenda.latest_media` returns bytes or a `Rejection`: 0 or ≥2 candidates → `MEDIA_MATCH_FAILED` (`attachment.unmatched`, no verdict); a non-200 or failed listing → `CHANNEL_UNAVAILABLE`. The download reuses `download` (host check, 10 MB cap) and the bytes go through `read_media` like `/caso` does. 120s covers the observed ~1s gap with margin for webhook retries.

**What would invalidate it.** The webhook starting to carry the uuid or `media_url` directly, or the webhook's and the listing's clocks diverging by more than 120s in production.
