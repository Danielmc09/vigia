# ADR-039 · Schemeless host: taken whole, accepted by its last label plus URL evidence (2026-10-27, Claude Code; revised 4 times same day)

**Context.** Incidents c-0051..c-0053: "The payment arrived.Bancolombia confirmed..." extracted `pago.bancolombia`, triggering a hard `brand_off_domain` on a legitimate message. The first fix (a short TLD allow-list) let the regex backtrack to a prefix whose TLD was listed: `chase.com.secure-login.ru` extracted as `chase.com`, an OFFICIAL domain (c-0054..c-0056). A second revision (any lowercase 2-letter label counts as a host) produced new false positives ("listo.Bancolombia/Davivienda las dos", "Thanks.Chase/Wells ok") and false negatives ("chase-verify.me:8080", "nequi-seguro.me" without a path). A third round found that with a hyphen, any lowercase word counted as a TLD, turning ordinary prose into a scam verdict.
**Options.** A public suffix list (tldextract: a dependency plus a network snapshot); a closed TLD list with nothing else (false negatives on .ru/.pw/.cn); always require a scheme (loses `bit.ly/x`, how scams are actually written).
**Decision** (final, replaces the patches with one rule): a schemeless host is taken whole, greedily — accepted entirely or discarded, never cut at an inner dot. `_accepts_host` looks at the last label plus a single evidence list: **strong evidence** = a path, port, query or fragment; **weak evidence** = a `www.` prefix (any case) or a hyphen in some label, which only counts if the last label is 2 letters or is in `SCHEMELESS_TLDS`. With strong evidence, any 2-24 letter alphabetic label is accepted (subject to the sentence-case rule below); with only weak evidence, only a 2-letter or listed label. A last label in Sentence Case (e.g. "Bancolombia", "Com") is accepted only if it's in `SCHEMELESS_TLDS`. With no evidence at all, the label must be in `SCHEMELESS_TLDS` and not in sentence case. With an explicit `https?://` none of this applies: any TLD and any Unicode letter is accepted (so `https://bancolómbia.com` still yields `lookalike_domain`).
The list covers generic TLDs (com, net, org, info, biz, gov, edu, int, example), abused new gTLDs (app, dev, page, xyz, top, zip, mov, site, online, shop, store, live, click, link, icu, cfd, buzz, rest, sbs, vip, club, win, bid, lat), and common LATAM/US/abuse ccTLDs (co, us, mx, ar, cl, pe, ec, ve, br, es, uk, ru, cn, pw, tk, ml, ga, cf, gq, ly, gl, io, cc, ws, su). Deliberately excluded: ccTLDs that are also ordinary words (me, te, so, it, ya, se, lo, la, de, en, no, si, to, is, in, on, at) and `ai` — these only get extracted with real evidence.
**Why.** Deciding on the last label of the whole host removes the backtrack-to-official-prefix bug; a single evidence list replaces ad hoc special cases and makes explicit what gives away a schemeless URL. Deterministic, no dependencies.
**Accepted ambiguity.** "Bancolombia-Nequi.me avisas" is lexically identical to a known scam shape (hyphen + 2-letter label); it gets extracted and flagged `brand_off_domain` — resolved by the analyst with context (T-09), not a regex. **Accepted risk.** A bare `bancolombia.me`/`nequi.me` with no hyphen, path, port, query or `www.` doesn't get extracted; if this shows up in a real scam, its TLD gets added with an eval.
**Deferred.** Punctuation glued to a word (`nequi.me?thanks`) is read as a query/fragment and still extracted — fix via incident evals. Lowercase prose with a listed TLD word after the dot ("pagué por bancolombia.co") still triggers `brand_off_domain` — pre-existing in HEAD, not introduced here; fix via incident evals.
**What would invalidate it.** A new abused gTLD outside the list and with no evidence not being extracted (add it via an eval); a legitimate 6+ letter domain hitting the Levenshtein threshold under a different suffix (see D-031).

**Addendum 2026-10-31 (deviation, incidents c-0232..c-0235):** the evidence rule above never actually reached the repo (missing from `urls.py` history and from `casos.jsonl`). What shipped was narrower: a list or 2-letter label, and Sentence Case always read as prose. Result: `pagos-dian.support`, `dian-pagos.help/x` and `Bit.Ly/3xQ` produced no URL and no signal at all. Implemented now, narrower than documented above: evidence = only a path or port (what `_URL` already captures; query/fragment-without-path and `www.`/hyphen as weak evidence were NOT implemented). Sentence Case: still read as prose unless there's evidence AND a known label (2 letters or listed), so `Bit.Ly/3xQ` and `Chase-Secure.Help/login` are extracted while `listo.Bancolombia/Davivienda`, `quedó.Su cuenta`, `us.Support is` are not. The list grew with `support, help, services, center, cyou, bond` (abused, not Spanish words). A path does NOT unlock labels outside the list; it only unlocks Sentence Case for a *known* label. `_FILE_EXTENSIONS` removed (unneeded) after a path-based false positive on `factura.xlsx/csv` and on legitimate paths like `bancolombia.ahorros/corriente`.
**What would invalidate it (addendum).** `pagos-dian.soporte` (unlisted TLD) still not extracted; `ok.Me/dijo` (2-letter Sentence Case with a path) extracted with no signal — each gets its own incident fix; a newly abused TLD gets added to the list.
