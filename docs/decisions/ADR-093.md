# ADR-093 · The panel form uploads files with the stdlib multipart parser and the webhook's own reader (2026-10-30, Claude Code)

**Context.** T-22f: Wazenda stores attachments but its API doesn't allow downloading them, so the video's Voice and SAM scenes must come from the panel's form. TAREAS said "the multipart `/caso` already supports" — false, `/caso` only takes JSON and `python-multipart` isn't installed (deviation noted).

**Options.** (a) add `python-multipart` and use `UploadFile` — a new dependency for one form. (b) stdlib `email.parser.BytesParser` over the body read with `read_capped` (10 MiB + 64 KiB of form overhead) — no dependency, and the cap cuts before parsing. (c) a separate endpoint for files — duplicates token, cap, and rendering.

**Decision.** (b). `_form_fields` in `app.py`. The file goes through `whatsapp.read_media` (sniff, ogg→wav, reader lookup, dedupe, `checked` with Voice/PDF caps and D-077's pixel cap), now also used by the webhook. Reading steps (`transcribe`, `read_image`, `decode_qr`, `read_pdf`) are prepended to `row.tools` so the orchestration is visible. Read in the pack's language (Voice uses `languageBias`); notices show in the panel's language.

**Note (reviewer).** Steps are named `read_image`/`read_pdf`, not `crop`: the image reader doesn't report whether SAM cropped, and showing `crop` without knowing would misrepresent the video. `Media`, `Sender`, and `read_media` stay in `services/whatsapp.py` even though they're no longer WhatsApp-only; moving them to `services/transcription.py` is deferred debt (large diff, no behavior change).

**What would invalidate it.** The `email` parser mishandling a real browser multipart body (binary with CRLF or non-ASCII names) — then switch to `python-multipart`; the form needing multiple files at once.
