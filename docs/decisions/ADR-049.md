# ADR-049 · Escalations persisted in `escalations` with the target encrypted; `transfer` changes roles in one statement (2026-10-27, Claude Code)

**Context.** specs/12 B7 (`transfer +57...`) needs an escalation to survive between two messages (`transfer`, then `confirm {id}`).
**Options.** (a) in-process memory (lost on restart, doesn't scale past one replica); (b) Redis (layer 2, doesn't exist yet); (c) another Postgres table with RLS by `business_id` like the rest.
**Decision.** (c), migration `0006_escalations.sql`: PK `(business_id, id)`, `target_enc` sealed under the business's DEK (the target is a phone or email, specs/16), `status` with a CHECK constraint. `store.save_escalation` upserts state; `store.find_escalation` is scoped by the business in context (another business's escalation is invisible, by RLS). The ownership swap is `store.transfer_ownership`, one atomic RLS-scoped `UPDATE`. Only transfers to an existing, non-owner member of the same business. The clock is the server's `datetime.now(UTC)`, not the channel's `received_at`, so a stale message can't reopen an expired escalation. `confirm` from `local`/`eval` never executes (tested). Only `transfer_ownership` has an executor; `report`/`block_sender`/`delete_case` reply `escalation.not_allowed` until T-10 wires them.
**Why.** No new infrastructure, RLS reused, atomic.
**What would invalidate it.** Several replicas confirming the same escalation concurrently (doesn't happen today: one owner, one message) → a `WHERE status = 'pending' RETURNING` guard would be added.
