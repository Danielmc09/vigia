# ADR-026 · Allow-list lookup before business context: scoped SECURITY DEFINER functions (2026-10-27, Claude Code)

**Context.** An incoming message's business isn't known yet, but `members` has forced RLS and returns zero rows without context; rejections also need to be logged.
**Options.** An allow-list table without RLS; connect as superuser for the lookup; scoped `SECURITY DEFINER` functions.
**Decision.** `vigia_find_member(hash)` returns only `(member_id, business_id, role)` by `phone_hash` or `email_hash`, and `vigia_record_rejection(hash, origin)` inserts into `rejected_attempts` (forced RLS, no policy, no GRANT to `vigia_app`). Both have a fixed `search_path`, EXECUTE revoked from PUBLIC and granted to `vigia_app`.
**Why.** The app gains no general read access to any table; with a hash it only gets an id, not PII.
**What would invalidate it.** The function owner on Railway not bypassing RLS (functions must be created by the migration role, a superuser), or a hash enumerator (mitigated: the hash is keyed).
