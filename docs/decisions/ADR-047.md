# ADR-047 · `commands.py` parses `confirmar`/`cancelar`/`transferir` like any other command (2026-10-27, Claude Code)

**Context.** specs/12 B7 (`transferir +57...`) and confirming escalations (`confirmar {id}`/`cancelar {id}`) need a free-text argument extracted before reaching `policy/actions.py`.
**Options.** Let `policy` parse raw text itself (duplicating `services/commands.py`'s grammar); add the three entries to `_GRAMMAR` in `commands.py`, alongside `enroll`/`team`.
**Decision.** The second. `commands.py` already owns the channel's command grammar; policy should only know typed actions (`EscalationAction`, an id, a phone), never raw user strings. Handlers read the named regex groups and call `policy.actions` with domain types. An `id` requires 8 hex digits (what `new_escalation` generates), so a forwarded "confirmar compra" message stays a case to analyze.
**Why.** One command grammar avoids two regexes for "the same" command drifting apart.
**What would invalidate it.** `confirmar`/`cancelar` needing conversational context `commands.py` doesn't have → becomes a channel dialogue step, not a one-line command.
