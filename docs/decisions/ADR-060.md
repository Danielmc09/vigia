# ADR-060 · Loop limits: 6 turns, 25 s, last turn without tools, one retry with the error as data (2026-10-27, Claude Code)

**Context.** specs/03 fixes 6 steps and 25 s per case, and asks that an invalid output be retried once with the error as data; otherwise a degraded verdict.

**Decision.** `src/vigia/analyst/loop.py:investigate`. `MAX_STEPS = 6`; on turn `MAX_STEPS - 1` tools are no longer offered, forcing the model to answer the schema. `DEADLINE_S = 25` is deducted from each call's `timeout_s`. An invalid response → one `RETRY` message with the pydantic errors (never the model's free text) and one more turn; a second invalid response, a model rejection, or hitting the limit → `None` (`degraded=True` on the verdict). Free text accompanying `tool_calls` is discarded and never fed back (rule 14); `reasoning` only goes to `AnalystResult.explanation` (logs). Analyst-sourced signals enter as `light`/`source="analyst"`, ids `[a-z_]{1,40}` only, max 5: they never trigger hard rules. The panel (T-13) never shows the analyst's `signals[].type` or its `explanation` — those are model-chosen text; the panel only shows deterministic signals with their i18n key (rule 14). `alert_team` and `report` are declared to the model but always return `POLICY_ONLY` as data (specs/03, specs/05).

**Revision 2026-10-27** (judge T-09, incidents `adv-analista-tope-pasos`, `adv-analista-deadline-herramientas`, `adv-analista-nombre-herramienta`, `adv-analista-costo-busqueda`):
1. The retry counts inside the 6: at most 6 model calls (was 7). An invalid response on turn 6 gets no retry: `None`.
2. The deadline is an instant (`monotonic() + DEADLINE_S`) checked before each model call **and before each tool call**; a tool that no longer fits cuts the loop (`None`). Each tool gets the remaining time (`Tool = Callable[[str, float], dict]`); `web_search` passes it to `SparkClient.web_search`, which uses `min(SEARCH_TIMEOUT_S, remaining)`. Real ceiling: `httpx` applies `timeout` per phase (connect, write, pool, each read), not to the total, so overshoot is bounded by the in-flight call — measured in T-14.
3. `tools_used` only stores names from `TOOL_SPECS`; any other name the model sends is stored as the literal `unknown_tool` (rule 14).
4. A tool with a cost returns it under the `usd` key; the loop strips it before sending the response to the model and puts it on its `tools_used` entry. The case total in `measure.py` is still the `SparkClient.usd` diff (which already includes search): `tools_used[].usd` is a breakdown nobody sums, so there is no double count.

**Revision 2026-10-27, round 2** (judge T-09, minor):
5. `MAX_TOOL_CALLS = 4` per turn; extra calls in the same turn are dropped (neither run nor echoed back). Why 4: specs/03's heaviest case uses `analyze_url` + `check_country` + `check_address_book` + `web_search`, one each; more than 4 in one turn only multiplies cost and time inside the 25 s budget.
6. `ModelTurn.model` is always the configured `MODEL` in `model/spark.py`, never the provider's returned `model` string: that is external text that would otherwise reach `Verdict.model`/`tools_used` (rule 14).

**What would invalidate it.** Real cases needing more than 4 tools (raise `MAX_STEPS` with cost measurement).
