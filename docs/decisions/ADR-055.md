# ADR-055 · `transfer` to a non-member replies as if the request were valid, without creating the escalation (2026-10-27, Claude Code)

**Context.** Incident `adv-enumeracion-transferir`: `team +X` then `transfer +X` distinguished a free number (added, "reply confirm <id>") from a number enrolled in another business (`transfer.not_member`, D-053), another 2-step oracle.
**Options.** (a) keep `transfer.not_member` (leaks); (b) actually save the escalation and fail at `confirm` (writes rows for strangers, moves the oracle to `confirm`); (c) reply `escalation.transfer_requested` with a fresh id, without saving anything.
**Decision.** (c), in `services/enrollment.py:_transfer`: for any number that isn't an active employee of this business (free, in another business, or the current owner), an escalation id is generated for the reply but never persisted; `confirm <id>` then replies `escalation.unknown`.
**Why.** The smallest change that equalizes step 2's reply without writing third-party data; the id is random and reveals nothing.
**Known residual oracle.** Step 3 (`confirm` over WhatsApp) still distinguishes, because a real ownership transfer is observable — closing that would mean lying about an irreversible action, so it's deferred to T-10 with per-business/per-hour escalation caps.
**What would invalidate it.** Support needing to explain to an owner why a transfer failed → validate against the owner's own team list via a read-only command that never queries other businesses.
