# ADR-077 · Images: 10 MB / 25 Mpx caps declared before decoding, SAM capped at 8 boxes by area (2026-10-28, Claude Code)

**Context.** Judge T-12 (MAJOR, incidents `adv-imagen-pixeles`, `adv-sam-cajas`): a 690 KB PNG declaring 13000×13000 passed `check_image` (magic bytes only), Spark billed it, and zxing decoded it whole (~2 GB RSS); Pillow only blocked over 2×89M px. SAM could return N boxes, each cropped and re-decoded.

**Decision.** `domain/image.py:check_canvas` opens the image lazily (header only) and compares declared width×height by hand against `MAX_IMAGE_PIXELS = 25_000_000` → `TOO_LARGE` (no warnings filter: `catch_warnings` isn't thread-safe); `Image.MAX_IMAGE_PIXELS` stays at the same value as a backstop; unreadable header → `INVALID_ATTACHMENT`. `check_image` checks in order: size > `MAX_ATTACHMENT_BYTES` (10 MB) → `TOO_LARGE`, magic bytes, header; `open_image` runs `check_canvas` before `load()`, so `decode_qr`, `crop`, and `image_phash` inherit the cap. Typed rejection with i18n key `image.too_large`, never an exception. Boxes: `largest(boxes, n)` sorts by area; `qr_urls` crops the `MAX_BOXES = 8` largest, and the analyst's `crop_tool` returns the `MAX_MATCHES = 5` largest (was the first 5).

**Why.** A phone screenshot is around 3 Mpx; 25 Mpx at 75-100 MB per decode is affordable even decoded up to 9 times (whole + 8 crops). 8 boxes comfortably fit a QR, a logo, and a button with margin.

**What would invalidate it.** Real large screenshots (>25 Mpx) that need reading, or real QR codes falling outside the 8 largest boxes.
