# ADR-091 · Per-business case number (`case 14`), not a random base32 (2026-10-30, Claude Code)

**Context.** The first real test showed the case UUID in the reply: 36 characters, two lines, impossible to type in `scam confirmed <id>` (incident `inc-id-caso-uuid`, T-10b). A short id, unique within the business, was needed; the UUID stays in the panel and API.

**Options.** (a) a per-business sequence: `businesses.case_seq` incremented via `UPDATE ... RETURNING` in the same statement as the case `INSERT`; unique index `(business_id, ref)`. (b) a random 4-5 char Crockford base32: doesn't reveal volume or order, but needs collision retries and is harder to type (uppercase, O/0 confusion). (c) derive the id from UUID bits: no uniqueness guarantee.

**Decision.** (a). `cases.ref` + `businesses.case_seq` (migration 0009, same per-business RLS). `save_case` returns the number or `None` if duplicate; `Case.ref` carries it to `whatsapp_message(..., case_ref=)`; `message.id_line` is `caso {ref}` / `case {ref}`; `scam confirmed <n>` looks up by `ref`.

**Why.** One SQL statement, no retries; the business row's lock makes it impossible for two cases to share a number. Digits only: typed without double-checking. The number revealing how many cases a business has had doesn't matter: only its own members see it. Cases saved before this migration keep `ref NULL`. `confirm <id>` still uses the escalation's 8-hex id (D-047): no escalation hangs off a case today.

**What would invalidate it.** The business row's lock, held while models run (the transaction spans the analysis, T-16), causing a visible wait for a second message from the same business — then a short separate transaction for the number, or base32 with retry.
