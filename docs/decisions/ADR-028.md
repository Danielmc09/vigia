# ADR-028 · Caps on email verification codes (2026-10-27, Claude Code)

**Context.** `my email` and `team ... <email>` send a code to any address; without a cap, VIGIA becomes a spam relay off our sending domain (Resend). The code is 6 digits and `code` wasn't counting failures: brute force over 10^6 attempts via WhatsApp.
**Options.** No caps, trust the channel's global cap (doesn't exist yet); a Redis counter (doesn't exist yet); a counter in the `verification_codes` table itself.
**Decision.** A Postgres counter. At most `VIGIA_EMAIL_CODES_PER_HOUR` (default 3) codes per member in a sliding hour, counting used and expired ones too (redeeming expires a code instead of deleting it, so redemption doesn't reset the count). Each failed attempt adds 1 to `attempts` on every live code for that member; past `VIGIA_CODE_MAX_ATTEMPTS` (default 5) codes stop working and the reply is `email.code_locked`. Values in `Settings`, migration `0003_code_limits.sql`.
**Why.** No new infrastructure, inside the same RLS-scoped transaction; 3×5 = 15 attempts/hour against 10^6 combinations gives ~1.5·10^-5 odds of guessing in an hour; 3 emails/hour is enough to fix a typo.
**What would invalidate it.** An owner enrolling many employees with other people's emails (the cap is per member, not per business: the owner is trusted for now); Redis in layer 2 (the counter would move there); real complaints from users locked at 3/hour.

**Revision 2026-10-27 (T-05b, specs/12 B4):** specs/12 B4 says "3 failed attempts" and the spec rules the code, so `VIGIA_CODE_MAX_ATTEMPTS` drops from 5 to 3: 3 codes × 3 attempts = 9/hour per address. `code` with no live code (expired, already used, or never requested) now replies `email.code_none` instead of `email.code_invalid` (specs/12 B3); `CodeCheck` adds `"none"`.

**Revision 2026-10-27 (incident `adv-relay-correo`, judge T-04):** the premise "the owner is trusted" was false, because any number becomes an owner with `hi X CO`, and `team` creates a new member on every call, so the per-member cap reset: `team +57300000NNNN A victim@...` cycling NNNN sent unlimited emails to someone else's address. **Decision:** replace the per-member cap with two sliding-hour caps: `VIGIA_EMAIL_CODES_PER_HOUR` (default 3) per **destination address** (email hash, counted across all businesses via the `SECURITY DEFINER` function `vigia_recent_email_codes`, which only returns a count) and `VIGIA_EMAIL_CODES_PER_BUSINESS_HOUR` (default 10) per **business**. Migration `0004_code_caps_by_address.sql`. **Why.** The per-address cap protects the victim from being used as a relay and also bounds brute force against one address (still 3×5=15/hour); the per-business cap bounds how many distinct addresses one business can touch (10 is enough for a 2-10 person team). If a cap trips, `team` still adds the member but reports the code didn't go out. Accepted cost: an owner can infer an address received ≥3 VIGIA codes in the last hour. **What would invalidate it.** An attacker with many WhatsApp numbers creating businesses to touch many distinct addresses (would need a global or per-unenrolled-sender cap, layer 2 with Redis).
